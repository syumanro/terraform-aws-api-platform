# 日本語学習ガイド

[中文版本](learning-guide.md) · [ビルド・デプロイ設定の行別解説](deployment-line-by-line.ja.md)

現在の Terraform ファイルは HashiCorp が推奨するシンプルな `#` コメントを使い、機能の区分を短い英語で示しています。装飾的な区切り線や行ごとの解説は付けず、詳しい学習説明はこのディレクトリのドキュメントに残しています。空行は読みやすさのための区切りです。Dockerfile、ビルド、デプロイ、タスクテンプレート、ローカルプレビュースクリプトは、[行別解説](deployment-line-by-line.ja.md)で学べます。JSON はコメントを直接追加できないため、元のテンプレートを維持しています。`app/` の画面、スタイル、画像はデモ用で、今回の学習範囲はインフラとデプロイの流れです。

説明は現在のコードの動作に基づきます。ログ保持日数、スケーリングしきい値、待機時間など、要求の裏付けがない値は、影響と選択の意味を説明しています。推測を作者の確定した設計意図として扱いません。今回の変更は説明の追加と整形のみで、設定値の変更やデプロイは行っていません。

## 最初に覚える構文

| 記述 | 意味 | この形にする理由 |
| --- | --- | --- |
| `resource "aws_subnet" "ecs_a"` | 種類が `aws_subnet`、内部名が `ecs_a` のリソースを宣言 | 内部名は Terraform アドレスの一部で、AWS の Name タグとは別です |
| `variable "vpc_id"` | 呼び出し側が渡せる入力を宣言 | 環境パラメータとモジュール実装を分け、再利用しやすくします |
| `var.vpc_id` | 現在のモジュールの入力を参照 | 子モジュールには親の全変数が自動継承されないため、明示的に渡します |
| `aws_subnet.ecs_a.id` | 作成した別リソースの ID を参照 | Terraform が参照から依存順序を推論するため、通常は `depends_on` を手書きしなくて済みます |
| `module.network.ecs_subnet_ids` | モジュールが公開した output を参照 | 呼び出し側が内部リソース名へ依存せず、公開インターフェースを使えます |
| `locals` / `local.xxx` | モジュール内部の計算値を定義・参照 | 式を再利用し、実装の詳細を外部引数として公開せずに済みます |
| `condition ? A : B` | 条件が真なら A、偽なら B | ここでは証明書が null かどうかで HTTP/HTTPS を選びます |
| `null` | 未指定または任意設定の省略 | 空文字列や文字列 `"null"` とは異なります |
| `{ ... }` / `[ ... ]` | オブジェクトや設定ブロック / リスト | 階層や複数要素を表現します。文字列リストの要素には引用符が必要です |
| `jsonencode(...)` | HCL データから JSON 文字列を生成 | ECS や ECR が必要とする JSON を作り、手書きのエスケープやカンマの誤りを避けます |
| `lifecycle.ignore_changes` | 指定項目の更新時の差分を無視 | 別システムに管理を任せられますが、意図しない変更も Terraform から修正できなくなります |

例えば `target_group_arn = module.load_balancing.production_target_group_arn` では、左側が ECS モジュールへの入力名、右側が負荷分散モジュールの出力です。実際の ARN を渡すと同時に、ターゲットグループを先に用意してから ECS を設定する依存関係を作ります。入力名と出力名は同じである必要はありませんが、意味と型を対応させます。

## 実際の流れに結び付けて理解する

要求は `Internet → 公開 ALB → プライベートサブネット内の ECS タスク（コンテナ 80 ポート）` を通ります。ALB は 2 つのパブリックサブネットに配置し、証明書があれば HTTPS を終端します。証明書が null なら HTTP を使い、ポート番号 443 だけでは暗号化されません。セキュリティグループによるアクセス制限と、ルートテーブルによる経路の両方が必要です。

公開は `GitHub → CodePipeline Source → CodeBuild のビルド・テスト → ECR イメージ + S3 成果物 → 手動承認 → CodeDeploy → 新 ECS タスクセット` の順です。GitHub はソース、ECR はイメージ、S3 はパイプラインのファイル、state バックエンドは Terraform のリソース状態を保存します。

パイプラインは `taskdef.json` の `<IMAGE1_NAME>` を `imageDetail.json` のイメージ URI に置き換えます。新タスク定義を登録すると、`appspec.yaml` の `<TASK_DEFINITION>` も実際のタスク定義 ARN に置き換えます。プレースホルダー自体は、そのまま実行できるイメージアドレスや ARN ではありません。

## 現在の構成で理解すべき制約

以下は学習のための観察です。今回の注釈追加で機能を修正した項目ではありません。

- プライベートサブネットには NAT 向け既定ルートがなく、必要な VPC Endpoint もこのリポジトリでは定義していません。ECS の送信許可だけでは経路を補えず、イメージ取得、ログ送信、ECS Exec のアクセス経路を別途用意する必要があります。
- 可用性ゾーンが 2 つでも、タスクが 2 個あるとは限りません。初期タスク数とスケーリング下限は 1 で、ゾーン間の冗長性を提供できません。
- テスト入口 10443 の受信範囲は `0.0.0.0/0` で、内部テスターに限定していません。ALB の既定動作も転送するため、Host 一致ルールだけでは完全なアクセス制限になりません。
- Terraform の初期タスクは `httpd:latest`、公開イメージは Nginx Dockerfile で、2 つのタスクテンプレートは一致しません。初期タスクは一時ボリュームを `/` にマウントするため、イメージ内のファイルへの影響を確認する必要があります。永続ストレージを設定済みという意味でもありません。
- ALB のヘルスチェックは `/`、ビルドテストと Dockerfile は `/health` を使います。1 つの成功で別の経路も検証済みとは判断できません。
- CPU とメモリには、それぞれ step scaling と target tracking の両方があります。ポリシーを合わせて読み、独立した制御として解釈しないことが大切です。しきい値と目標利用率は実際の負荷で検証します。
- IAM ロール、VPC、state バケットは既存リソースが前提で、このリポジトリは作成しません。`prd` プロファイル名はアカウントの正しさを証明せず、固定 ARN は別アカウントでの再利用も制限します。
- state は S3 にありますが、同時実行ロックを設定していません。集中保存だけで複数人の同時操作が調整されるわけではありません。
- CodePipeline の手動承認でデプロイ開始を判断し、CodeDeploy はデプロイグループの設定に従って Blue/Green を切り替えます。別の段階なので、公開状況はそれぞれ確認します。
- ECR は同名タグを上書きできず、ビルドのタグはコミット ID の先頭 12 文字です。同一コミットを再ビルドすると push が失敗する場合があります。30 イメージ保持も、それ以前の版へのロールバックを保証しません。
- 固定名と `create_before_destroy` の組み合わせは名前衝突を起こす場合があり、この設定だけで無停止置換は保証できません。

`terraform validate` は設定構造と Provider インターフェースを検証します。実際の通信経路、権限、デプロイ待機フローの成功は保証しません。コメントを理解した後は plan と実際の検証で個別に確認し、現在の値をそのまま本番の推奨値と考えないようにしましょう。
